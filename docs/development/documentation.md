## 1. 最少文档原则

**默认不新增文档，优先更新现有文档。**

- 不为每个功能生成独立计划、实施说明、进度记录、测试报告、完成总结或交付报告，除非用户明确要求。
- 只有运行方式、长期维护流程、重要约束、业务概念及无法从代码理解的关键决策值得长期保存。
- 代码能准确表达的信息不重复复制；同一信息只维护一个权威来源。
- 不按日期、Issue 编号、单个功能或开发阶段组织长期文档。

准备新增文档时先判断：

1. 是否只是当前任务的计划、排查、实现或验证过程？是则留在对话、Issue / PR，必要的临时文件放 `.local/`。
2. 三个月后，其他开发者或 Agent 是否仍需要主动读取？以此判断长期价值，不把三个月作为硬性期限。
3. 现有文档是否有合适位置？有则更新，只有主题独立且无法合理承载时才新建。

目标是让长期文档越来越准确，而不是越来越多。

## 2. 信息归属

| 信息 | 权威位置 |
| --- | --- |
| 需求、Bug、TODO、验收标准 | GitHub Issues |
| 当前实现与实际改动 | 代码、配置、Commit / Diff；行为需真实验证 |
| 单次审查、交付和验证记录 | Issue / PR |
| 临时计划、排查和实验 | 对话；需要落盘时放 `.local/` |
| 项目入口、启动和基本配置 | `README.md`、`.env.example` |
| AI 核心规则和专项规则入口 | `AGENTS.md` |
| 开发及文档治理细则 | `docs/development/` |
| 系统结构、业务概念、重要决策 | 对应长期文档，按需创建 |
| 部署、升级、回滚和恢复 | `docs/operations/` |
| 必要接口规范、协议和技术参考 | `docs/reference/` 或官方来源 |

Notion 保存通用协作方法与跨项目知识；仓库保存当前项目长期知识。不要在 Notion、仓库和 GitHub 重复人工维护同一内容。

## 3. 仓库入口

### README.md

保存项目用途、安装与启动、必要配置、测试和构建命令、关键目录与文档入口。不放任务进度、TODO、开发日记、单次任务说明或已完成功能流水账。

README 能说清的内容不再拆成专项文档。

### AGENTS.md

保存项目级核心约束、验证底线和专项规则读取入口，详细流程交给对应专项文件。工具不自动读取时，通过其支持的规则入口引用，不复制多份完整规范。

### .env.example

只保存环境变量示例和必要说明，不包含真实密钥、密码或 Token。

## 4. docs 目录

保持浅层结构，原则上不超过两层子目录。沿用项目现有结构，不为统一目录而重构；以下文件和目录按需创建，不生成空目录或占位文件。

```
docs/
├── architecture.md          # 当前系统结构、模块边界、关键数据流
├── domain.md                # 长期稳定且容易误解的业务概念
├── decisions.md             # 重要决策、原因及影响
├── development/
│   ├── workflow.md          # 开发、GitHub、验证和交付
│   └── documentation.md     # 文档治理
├── operations/              # 部署、升级、回滚、备份和恢复
└── reference/
    └── api/                 # 必要接口规范，如 OpenAPI 文件
```

- `architecture.md` 描述当前结构、核心模块、边界、数据流和外部依赖，不记录每次修改历史。
- `domain.md` 只解释长期稳定的业务概念及关系，不堆技术实现细节；概念简单时无需单独创建。
- `decisions.md` 集中记录少量重要决策，每项简述背景、决定、原因和影响。只有复杂且需要独立追踪时再拆成独立 ADR。
- `development/` 可按需容纳特殊测试流程及接入约束；普通启动或测试命令仍放 README。
- 接口优先维护可验证的规范或引用官方文档，不反复手写容易过期的接口说明。
- 文档与实际代码、配置和接口保持一致。重要约束和决策不要只埋在 Issue 评论中；当前行为与文档冲突时先核实，再判断应修代码还是文档。

## 5. 本地临时目录

```
.local/
├── scratch/       # 临时计划、分析、排查和实验
├── logs/          # 运行日志和调试输出
└── artifacts/     # 截图、测试生成物和临时结果
```

- `.local/` 是临时工作区，不是第二套文档仓库；不要为每轮分析、计划或总结自动创建文件。
- `.local/`、真实环境配置和密钥加入 `.gitignore`，保留可提交的 `.env.example`。已经被 Git 跟踪的敏感文件不会因为新增忽略规则而自动变安全，发现泄露时需单独处理。
- 任务结束后清理本次产生且不再需要的临时内容；不擅自删除其他任务用途不明确的资料。
- 需要长期保存的证据整理、脱敏后附到对应 Issue / PR，不只留在某台机器上。

## 6. 调研与验证材料

调研、开发方案和排查默认属于过程材料。得出结论后，只把跨任务仍有效的规则或决策合并进对应长期文档，不永久保留整份过程。

验证结论简短记录在 Issue / PR，截图等证据可作为附件；自动检查使用 GitHub Actions 的真实记录。涉及外部资料的长期结论，保留必要来源链接和适用条件。

默认不创建 `TEST_REPORT.md`、`VALIDATION_REPORT.md`、`FINAL_QA.md` 等单次报告，除非用户明确要求正式报告。

## 7. 旧文档整理与删除保护

先迁移有价值的信息，再处理原文件：

| 旧内容 | 去向 |
| --- | --- |
| 待办、Bug、未完成需求 | GitHub Issues |
| 启动、配置 | README、配置示例 |
| 系统结构、业务概念 | 对应长期文档 |
| 重要长期决策 | `decisions.md` |
| 部署、回滚、恢复 | `operations/` |
| 已完成任务的计划、调试、验收过程 | 无独有长期价值后删除，必要证据留在 Issue / PR |

删除前必须：

1. 确认有价值的信息已迁移，未解决事项已有去处。
2. 检查 Git 跟踪状态和未提交修改；确认必要历史已提交或备份，不能仅因项目用了 Git 就认为资料可恢复。
3. 检查文档链接、脚本、工具或规则入口是否仍引用该文件，必要时更新引用。
4. 不覆盖或删除用户未明确授权处理的无关资料。

Git 历史可以保存已提交内容，但不会自动保存未跟踪文件或所有本地修改。不需要为了“怕丢”长期保留大量已确认重复的 Markdown，也不能以此为由直接批量删除。

## 8. 归档

只有确实暂时不能删除的旧资料才放 `docs/archive/`，明确标记“非当前开发依据”，并在可行时说明替代入口。

AI 默认不读取归档。不要把几百份旧文档原样搬入 archive 或 GitHub Wiki 后继续堆积。

**长期文档保留必须再次读取的知识；任务过程留在任务记录中。**
