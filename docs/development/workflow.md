## 1. 开发流程
1. 理解需求，阅读当前 Issue、相关代码及适用规则。
2. 明确目标、范围和验收标准；能自行判断的细节不反复确认。
3. 选择最简单的方案并完成实现。
4. 执行与改动匹配的真实功能验证，以及必要的构建、类型检查和测试。
5. 主动修复问题，无法解决时说明实际限制。
6. 简洁交付，并同步对应 Issue；不把未经验证的功能报告为测试通过。
## 2. GitHub Issues
**GitHub Issues 管任务，仓库文档管长期知识。**
- 需求、Bug、验收条件、待办和未解决问题统一记录在 Issues，不在本地重复维护需求清单、进度表或任务文档。
- 小修改可沿用相关 Issue；无需继续跟踪的微小修改不强制创建 Issue。
- 新功能、明显 Bug、跨模块修改、多个验收条件或需要后续跟踪的任务，应使用 Issue。
- Issue 至少说明目标和验收标准；背景、范围、不包含的内容在有必要时补充。简单任务几句话即可，不强制套用完整模板。
- 开始前阅读对应 Issue；完成后留下简短的修改摘要、实际验证结果和剩余问题。
- 满足验收条件后关闭 Issue；未解决事项保留或拆成后续 Issue，不把部分完成写成全部完成。
## 3. 修改范围
- 只修改满足当前需求和验收标准所必需的内容，不因“顺便更整洁”而扩大改动面。
- 不影响当前任务的额外 Bug、重构机会和技术债单独记录。
- 沿用现有技术栈、代码目录和组件，不为统一结构做无关重构。
- 不覆盖、回滚或混入用户已有的无关修改；多 Agent 避免同时编辑相同文件。
## 4. 真实验证
验证应对应验收标准，重点覆盖：
- 用户实际操作路径，而不仅是页面能打开。
- 真实接口和应当持久化的数据，以及必要的相关功能测试。
- 外部模型和异步任务的提交、状态查询、真实结果及失败处理。
- 必要的构建、类型检查和 Lint 等检查。
构建成功不等于功能通过，Mock 成功不能替代真实接口验证。未执行的检查不得写成“已通过”；未完成的验证说明原因和影响。
已配置并实际触发 GitHub Actions 时，使用与本次改动对应的真实 CI 结果作为自动检查证据。未配置、未触发或无法运行 CI 时，如实记录本地执行的验证，不声称 CI 通过。CI 也不能替代其未覆盖的真实业务路径验证。
## 5. Commit、分支与 PR
- 实际代码变更以 Commit 和 Diff 为准，不另外生成修改文件清单文档。
- 提交说明清晰，适用时关联对应 Issue；不把无关修改混入同一次提交。
- 默认在当前分支开发，不主动创建分支或 PR；用户明确要求或适用团队流程要求时再使用。
- 多人或多 Agent 并行时先协调文件和任务边界，需要时采用隔离分支，不因并行就自动增加流程。
- `feat`、`fix`、`docs` 等提交前缀可按项目惯例使用；`refactor` 不代表允许顺手扩大重构范围。
有 PR 时，简短说明问题或目标、主要变更、实际验证及关联 Issue；Bug 修复需要时补充根因。复用 PR 描述，不额外生成实施、测试或完成报告。
## 6. Projects 与 Releases
- 任务多、需要排期或多人协作时才使用 Projects，不默认给简单项目增加看板成本；状态沿用项目需要。
- 正式发布时使用 Releases 记录用户或维护者关心的新增、变化、修复和移除，不复制全部 Commit 流水账。
## 7. GitHub 不可用
GitHub 不可访问或权限不足时：
- 明确报告实际限制，不声称已创建、更新或关闭 Issue / PR。
- 必要时在 `.local/` 临时记录待同步信息，不建立第二套任务系统。
- 恢复访问后核对实际状态再同步，避免重复创建。
## 8. 交付
交付时简洁说明：
- 完成内容。
- 主要修改文件。
- 实际验证结果，包括未执行或未通过的项目。
- 剩余问题。
有对应 Issue 时同步完成记录。只有长期知识发生变化时才更新仓库文档；不额外生成交付报告文件，除非用户明确要求。
**用真实运行结果证明任务完成，不用文档数量证明做过工作。**
